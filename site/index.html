Dependency hallucination firewall

Your AI assistant just invented that package.

Code-generation models suggest dependencies that do not exist, and attackers register those names with malware inside. VaporDep checks every package name against the real registry and scores how much it looks like a slopsquatting trap — before it lands in your lockfile.

Many hallucinated names repeat across prompts, which makes them predictable — and a predictable non-existent name is a name an attacker can register first. Spracklen et al., We Have a Package for You! A Comprehensive Analysis of Package Hallucinations by Code Generating LLMs, USENIX Security 2025 — arXiv:2406.10279

This is slopsquatting: typosquatting where the typo is made by the model instead of the human. Vulnerability scanners cannot help — they audit packages that exist. VaporDep asks the question one step earlier: should this package exist at all?

How it works

Three steps, no account required for the first two.

1

Read the names

The CLI parses package.json, requirements.txt, Cargo.toml, Gemfile, composer.json and go.mod. The API takes names directly — from an editor plugin, a bot, or a script that intercepts model output.

2

Ask the real registry

Every name is validated against its ecosystem's naming rules, then looked up on npm, PyPI, crates.io, RubyGems, Packagist or the Go module proxy. Not a cached mirror — the registry itself.

3

Score the name

Missing packages are flagged. Names one or two edits away from a popular package — the hallucination signature — score higher. Existing packages get extra scrutiny when they are brand new, barely downloaded, have no repository, or shadow a popular name.

  • danger fails the build by default
  • caution is reported; fail on it with --fail-on caution
  • ok passes
FlagPointsTriggered when

Reading it

exists

Whether the registry knows the name. Never guessed: the API answers true or false; only the CLI's --offline mode reports null.

registry

Created date, last publish, weekly downloads, repository and description when the package exists — null for fields a registry does not expose, rather than an estimate.

risk

Level, score and every flag that fired, each with a human-readable message you can print straight into a CI log.

suggestions

Up to five popular packages within two edits, closest first. Usually the name the model meant.

FAQ

Questions people ask before trusting a security tool.

Is this open source?

Yes — MIT licensed, the whole thing: CLI, GitHub Action, the API (a Cloudflare Worker), the scoring rules and the data refresh script. You can read every line and self-host it on Cloudflare's free tier in a few minutes; the deployment guide walks through it. The paid plans exist for people who would rather pay a few dollars than run infrastructure: you are paying for convenience, not for access.

What is slopsquatting?

Typosquatting, but with the typo made by a language model. Models hallucinate plausible package names; when the same wrong name shows up across many prompts, an attacker can register it on the registry with a malicious install script and wait for developers to paste the model's suggestion. The USENIX Security 2025 study linked above measured how often models hallucinate package names in the first place.

How is this different from npm audit, Dependabot or Snyk?

Those tools look for known vulnerabilities in packages that exist. VaporDep asks whether the package should exist at all, and whether its name looks like a trap. The two are complementary: run VaporDep on the names, run your scanner on what you install.

Does the API store my dependency list?

The Worker has no database. A request is looked up against the registry, scored and returned; the only thing kept is Cloudflare's standard request logging and, for single-package checks, a five-minute HTTP cache. If that is still too much, run the CLI in local mode — it talks to the registries directly from your machine and never contacts VaporDep at all — or self-host the Worker.

Will it flag my own brand-new package?

A legitimate package published last week with a repository link scores 25 (caution), maybe 40 if downloads are still low. That is by design: new-and-unknown deserves a second look, not a block. The default --fail-on danger only fails the build on missing packages, invalid names, or existing packages that stack several warning signs. Packages that live only on a private registry will show as NOT_FOUND; point the check at your public manifests only, or pass a plain text file of just the names you want checked together with --ecosystem.

What does --offline do?

No network at all. Only the naming rules and the similarity check against the bundled popular-package lists run, so exists is reported as null and near-misses come back as caution. Useful in air-gapped CI or as a very fast pre-commit hook; it will not catch a hallucinated name that happens to be far from every popular package.

Where do the "popular package" lists come from?

From public ranking data (PyPI's download rankings, crates.io and Packagist's popularity APIs) and curated lists for the ecosystems without a free ranking endpoint: the npm list is re-verified against the npm registry on every refresh, the RubyGems and Go lists are curated and format-checked only. A scheduled job refreshes them monthly and commits the result, so the lists in the repository are the lists the API uses.
